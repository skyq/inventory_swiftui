# Как принимать один ответ небольшой модели

1. Карточка выполнена полностью, соседние задачи не захвачены.
2. В diff только нужные изменения; исходный ТЗ и утверждённые контракты не переписаны.
3. Публичные интерфейсы, DTO, схемы и версии не изменены без согласования.
4. Бизнес-правила проверены сервисом, а не только кнопками формы.
5. Есть фактические результаты нужных тестов. Для ядра `dart test`, для Flutter `flutter test`; анализ/форматирование по репозиторию. Native-тесты требуют реального Mac и не заменяются mock-ответами.
6. У затрагиваемой транзакции проверен rollback; у файлов — поведение ошибки и очистки; у unsafe-операции — сценарии RECOVERY_PROTOCOL.
7. Строки UI в ARB, core без Flutter, UI без SQL, новые сетевые запросы и телеметрия отсутствуют.
8. Обновлены HANDOFF.md и RUN_LOG.md. На конце этапа отдельно получено подтверждение владельца.

При ошибке отправлять модели отдельное узкое исправление: ожидаемое поведение → воспроизведение/тест → текущий сбой → разрешённые файлы. Не просить «заодно улучшить всю архитектуру». Если задание не помещается в реальный контекст, его нужно дополнительно разрезать по конкретному API/тесту, сохранив тот же контракт и критерий приёмки.

Ошибки протоколов импорта/миграций, схемы данных и поиска следует разбирать с опытным разработчиком. Самостоятельное «DONE» модели не считается приёмкой.
