# Inventory: разбиение ТЗ на задачи для модели 9B

Подготовлено 13 ноября 2026 по исходному `TZ_inventory_mvp.md`, версия 1.0.

Друг, вероятно, имеет в виду следующее: небольшую модель не просят «сделай всё приложение по этому ТЗ», а дают ей одну ограниченную задачу с текущим кодом, фиксированными интерфейсами и проверяемым результатом. После проверки результата передают следующую задачу.

**9B — примерно 9 миллиардов параметров модели. Это не размер её контекстного окна и не гарантия качества.** Конкретная модель и инструменты неизвестны, поэтому пакет не привязан к Ollama, LM Studio или другому запускателю. Даже такое разбиение не гарантирует, что любая 9B справится; ошибки нужно проверять, а сложную задачу при необходимости резать дальше по конкретному контракту.

## Порядок работы

1. Владелец/архитектор выполняет T00.01–T00.03: отвечает на D01–D12, проверяет реальный стек и фиксирует API. В репозитории будущего приложения появляются `DECISIONS_APPROVED.md`, `TOOLCHAIN.md`, `API_CONTRACT.md`, `RECOVERY_PROTOCOL.md`. В пакете эти файлы намеренно не выданы за уже согласованные решения.
2. После этого взять первую кодовую карточку, T01.01. Давать модели **одну** карточку за запуск. Выполнять очередь сверху вниз: зависимости нужны дополнительно к этому порядку. Нельзя обойти контрольную приёмку по сокращённой ветке графа.
3. Приложить только относящиеся к задаче утверждённые контракты, текущие интерфейсы/код/тесты и краткий `HANDOFF.md`. Релевантные выдержки самого ТЗ уже включены в карточку. Если модель работает с файлами, указать точные пути. Если это обычный чат, вставить содержимое нужных файлов; без доступа к коду модель не сможет надёжно «продолжать» существующий проект.
4. Проверить diff и запустить требуемые тесты. Ответ `DONE` не считается доказательством. Незапущенные обязательные проверки и недостающие входные файлы — `BLOCKED`, а не «готово на глаз».
5. Принятый результат сохранить в репозитории, обновить `HANDOFF.md` и `RUN_LOG.md`. Следующему запуску передать новое состояние файлов, а не надеяться на память модели.
6. После каждого из пяти этапов представить владельцу отчёт, инструкцию проверки, фактические результаты тестов и отклонения. Следующий этап начинается после подтверждения — это требование исходного §12.

## Как отправить одно задание

Текст из `tasks/T01.01.md` уже оформлен как готовый запрос. В обычном чате перед ним можно написать:

```text
Выполни только приложенную карточку T01.01.
Ниже — утверждённый контракт и входные файлы для этой задачи.
Не переходи к следующей карточке. Если не хватает файла или решения,
верни BLOCKED и перечисли, чего именно не хватает.
```

Не отправляй все 79 карточек одним запросом. Полное ТЗ оставь человеку для сверки. Модель должна видеть свою карточку, нужную часть контракта и актуальный код. Саму задачу выбора архитектуры/протокола восстановления лучше решает владелец с опытным разработчиком или более сильной моделью.

Если окно контекста всё равно мало, делить не по случайному числу строк: сначала чистый алгоритм и его тесты, затем адаптер, затем подключение к UI. Сохранить исходный ID с суффиксами `.a/.b/.c`, зависимости и единый контракт; критерий исходной карточки считается выполненным лишь после всех частей. Если проект уже частично существует, сначала сопоставить его текущие файлы с очередью и принять только реально проверенные карточки; не создавать вторую архитектуру рядом с первой.

## На что обратить внимание владельцу

В ТЗ есть места, где независимые исполнители могут получить разное поведение: передача в уже текущем статусе, возврат от архивного человека, пропуск места при возврате, создание человека внутри передачи. Все они вынесены в D02–D04/D08.

Технически важнее всего D01: транзакция SQLite не охватывает перемещение фотографий и папок. Для импорта/миграции нужен согласованный протокол копий и восстановления, включая WAL и прерывание приложения. В задачах с этой логикой указан обязательный человеческий review. Точный протокол не следует поручать небольшой модели изобретать в ходе отдельной карточки.

Для поиска отдельно проверяется «куртка» → «курточку»: один Snowball не заменяет тест всей поисковой цепочки. Пороги нечёткого совпадения подбираются на позитивных и негативных примерах, без специальных ответов для одного слова.

Это пакет заданий, а не обещание полностью автоматической разработки. Реализацию, нативные фотоисточники и производительность придётся проверять на настоящем Mac. Проверки приложения на этом шаге не запускались: приложения ещё нет.
