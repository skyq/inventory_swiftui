# Техническое задание: приложение для наведения порядка в вещах (MVP)

Рабочее название: **Inventory**. Версия ТЗ: 1.0. Документ предназначен для агента-разработчика.

---

## 1. Цель и контекст

Личное десктопное приложение для macOS, которое хранит каталог домашних вещей. У каждой вещи есть название, описание, фото и место хранения. Места образуют иерархию (комната → шкаф → полка). У вещи есть статус из редактируемого списка, а передачи вещей другим людям фиксируются в неизменяемой истории. Есть галерея и полнотекстовый поиск с устойчивостью к опечаткам и словоформам.

Принципы:
- Один пользователь, без аккаунтов и ролей.
- Все данные локальные, без сервера и синхронизации.
- Главная защита от потери данных: ручной бэкап и автокопии перед опасными операциями.
- Ядро (данные, правила, поиск) отделено от интерфейса, чтобы позже выпустить Android и iOS без переписывания логики.

## 2. Границы MVP

### 2.1. Входит в MVP
Места с иерархией, вещи с одним обязательным фото, теги, количество, заметки, статусы (редактируемые, архивируемые), справочник людей, передачи и возвраты, история, галерея (сетка и «По местам»), фильтры, поиск, экспорт и импорт архива, смена папки данных, автокопии перед импортом и миграцией.

### 2.2. Не входит в MVP (не делать)
- Синхронизация, облачный бэкенд, аккаунты, роли, мультипользовательность.
- Android и iOS (только задел в архитектуре).
- Камера, Continuity Camera, импорт из «Фото», импорт контактов macOS.
- Несколько фото у вещи; история фото.
- Вложенность вещей друг в друга.
- История перемещений между местами.
- Типы передач «насовсем / с возвратом», сроки возврата, напоминания, экран «у кого что сейчас».
- Деление записи при передаче части количества.
- Скрытие вещей по статусу, поведение, зависящее от статуса.
- Счётчики и подсказки «наведи порядок» на главном экране.
- Корзина и физическое удаление вещей и статусов.
- Редактирование и удаление записей истории; ввод даты задним числом.
- Ручной порядок и перетаскивание в «По местам»; ручной порядок статусов.
- CSV, печать, PDF.
- Дополнительные горячие клавиши и контекстное меню.
- Подпись и нотаризация, Mac App Store, автообновления.
- Периодические автокопии по расписанию.
- Слияние баз при импорте.

## 4. Технологии и архитектура

### 4.1. Стек (рекомендации, агент может заменить обоснованно)
- Flutter (stable), Dart, целевая платформа `macos`.
- БД: SQLite через `drift` (миграции, типобезопасные запросы, транзакции). Не использовать расширения SQLite, отсутствующие на мобильных платформах (в частности FTS5 и системные токенизаторы).
- Состояние: Riverpod (или аналог по выбору агента).
- Русский стемминг: Snowball (пакет для Dart или собственный порт).
- Файловые операции: `path_provider`, `file_selector`, `desktop_drop` (drag and drop), пакет для чтения изображений из буфера обмена (например `super_clipboard` или `pasteboard`), `shared_preferences` для настроек интерфейса.
- Декодирование HEIC: через платформенный слой macOS (ImageIO/CoreGraphics, нативный код на Swift через method channel), а не самописным декодером.
- Локализация: `flutter gen-l10n` (ARB). Язык один, русский; все строки выносятся в ARB.

### 4.2. Слои
```
inventory_core/        # чистый Dart-пакет, без зависимостей от Flutter
  domain/              # сущности и правила (циклы, статусы, передачи)
  data/                # репозитории интерфейсами, реализация на drift
  search/              # нормализация, стемминг, индекс, ранжирование
  backup/              # экспорт, импорт, манифест, версии формата
app/                   # Flutter-приложение (macOS)
  ui/                  # экраны, виджеты, тема
  platform/            # HEIC, буфер обмена, drag and drop, диалоги файлов
  l10n/
```
Требование: `inventory_core` не импортирует `dart:ui` и `package:flutter`. Работа с фото (декодирование, ресайз) спрятана за интерфейсом `ImageProcessor`, реализация для macOS лежит в `app/platform`.

### 4.3. Данные на диске
Папка данных (по умолчанию `~/Library/Application Support/Inventory/`, меняется в настройках):
```
inventory.db
photos/<uuid>.jpg
thumbs/<uuid>.jpg
logs/app.log
_safety/before-import/       # копия хранилища перед импортом (база и фото)
_safety/before-migration/    # копия файла базы перед миграцией
```
Путь к папке данных хранится вне этой папки (в `shared_preferences`).

Настройки интерфейса (размер плитки, сортировка, фильтры, дата последнего экспорта, включено ли напоминание о бэкапе) хранятся локально в `shared_preferences` и в архив не попадают. Настройки, связанные с данными (статусы по умолчанию), хранятся в таблице `settings` и попадают в архив.

## 5. Модель данных

Идентификаторы: UUID v4 (текст). Время: целое число, Unix time в миллисекундах UTC; в интерфейсе показывается в локальном часовом поясе.

```sql
CREATE TABLE places (
  id TEXT PRIMARY KEY,
  parent_id TEXT REFERENCES places(id) ON DELETE RESTRICT,   -- NULL = корневое
  name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  photo_file TEXT NOT NULL,        -- относительный путь, photos/...
  thumb_file TEXT NOT NULL,        -- thumbs/...
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE statuses (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  is_archived INTEGER NOT NULL DEFAULT 0,
  sort_order INTEGER NOT NULL,     -- порядок создания
  created_at INTEGER NOT NULL
);

CREATE TABLE people (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  phone TEXT NOT NULL DEFAULT '',
  notes TEXT NOT NULL DEFAULT '',
  is_archived INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE items (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  notes TEXT NOT NULL DEFAULT '',
  quantity INTEGER NOT NULL DEFAULT 1 CHECK (quantity >= 1),
  place_id TEXT REFERENCES places(id) ON DELETE RESTRICT,    -- NULL = «Без места»
  status_id TEXT NOT NULL REFERENCES statuses(id) ON DELETE RESTRICT,
  photo_file TEXT NOT NULL,
  thumb_file TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE tags (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,              -- как введено первым
  name_key TEXT NOT NULL UNIQUE    -- нормализовано: trim, схлопнутые пробелы, нижний регистр, ё→е
);

CREATE TABLE item_tags (
  item_id TEXT NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  tag_id TEXT NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (item_id, tag_id)
);

CREATE TABLE status_changes (      -- неизменяемая
  id TEXT PRIMARY KEY,
  item_id TEXT NOT NULL REFERENCES items(id) ON DELETE RESTRICT,
  from_status_id TEXT NOT NULL REFERENCES statuses(id) ON DELETE RESTRICT,
  to_status_id TEXT NOT NULL REFERENCES statuses(id) ON DELETE RESTRICT,
  comment TEXT NOT NULL DEFAULT '',
  created_at INTEGER NOT NULL
);

CREATE TABLE transfers (           -- неизменяемая
  id TEXT PRIMARY KEY,
  item_id TEXT NOT NULL REFERENCES items(id) ON DELETE RESTRICT,
  kind TEXT NOT NULL CHECK (kind IN ('give','return')),
  person_id TEXT NOT NULL REFERENCES people(id) ON DELETE RESTRICT,
  comment TEXT NOT NULL DEFAULT '',
  created_at INTEGER NOT NULL
);

CREATE TABLE settings (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
-- ключи: default_status_id, transfer_status_id, return_status_id
```

Триггеры неизменяемости:
```sql
CREATE TRIGGER status_changes_no_update BEFORE UPDATE ON status_changes
BEGIN SELECT RAISE(ABORT, 'history is immutable'); END;
CREATE TRIGGER status_changes_no_delete BEFORE DELETE ON status_changes
BEGIN SELECT RAISE(ABORT, 'history is immutable'); END;
-- то же для transfers
```

Индексы: `items(place_id)`, `items(status_id)`, `places(parent_id)`, `item_tags(tag_id)`, `status_changes(item_id, created_at)`, `transfers(item_id, created_at)`, `transfers(person_id)`.

Включить `PRAGMA foreign_keys = ON` для каждого соединения.

Начальные данные при создании нового хранилища (один раз): статусы «В наличии», «Одолжил», «Отдал», «Продал», «Выбросил», «Потерял», «В ремонте». Настройки: `default_status_id` = «В наличии», `transfer_status_id` = «Отдал», `return_status_id` = «В наличии».

## 6. Функциональные требования

### 6.1. Места
- Создание, редактирование (название, описание, фото, родитель), перемещение вместе со всем содержимым.
- Поля: название (обязательно, до 200 символов), описание, фото (обязательно), родитель (необязательно; пусто = корневое место).
- Глубина иерархии не ограничена.
- **Защита от циклов**: нельзя назначить родителем само место или любого его потомка. Проверка в доменном слое (рекурсивный запрос) и тест; в интерфейсе недопустимые варианты не предлагаются.
- **Удаление**: только если в месте нет вещей и вложенных мест. Иначе удаление запрещено, приложение показывает, что именно мешает (количество вещей и вложенных мест), и предлагает их переложить. При удалении места удаляются его фото и превью.
- Путь места (`Спальня / Шкаф / Верхняя полка`) всегда вычисляется из иерархии, нигде не хранится.
- Дублирование названия среди мест одного родителя разрешено, но приложение показывает предупреждение.

### 6.2. Вещи
- Поля: название (обязательно, до 200 символов), описание, заметки, теги (несколько), количество (целое ≥ 1, по умолчанию 1), статус (обязателен, по умолчанию из настройки), место (необязательно), фото (обязательно).
- Создание (Cmd+N) невозможно без фото. Форма не даёт сохранить, пока фото не добавлено.
- Редактирование всех полей, включая замену фото и перемещение (смену места). Смена места не пишется в историю.
- **Смена статуса не создаёт записи при обычном редактировании формы**: статус меняется только через действие «Сменить статус» (с необязательным комментарием), и это пишет запись в `status_changes`. В форме редактирования поле статуса недоступно для изменения (показывается только текущее значение). При создании вещи запись истории не создаётся.
- Смена на тот же статус запрещена.
- **Физического удаления вещей нет.**
- Количество — информационное число. Передача и статус относятся ко всей записи.

### 6.3. Теги
- Теги вводятся на вещи; при вводе работает автодополнение существующих тегов.
- Теги сравниваются без учёта регистра, лишних пробелов и различий «е/ё» (по `name_key`). Максимальная длина тега 50 символов.
- Тег без вещей удаляется автоматически. Пустые теги в разделе «Теги» создавать нельзя.
- Раздел «Теги»: список с количеством вещей; сортировка по имени и по количеству; **переименование** (если новое имя совпадает с существующим тегом, предлагается объединение); **удаление** (снимает тег со всех вещей, подтверждение с указанием количества вещей); **объединение** двух тегов в один с выбором итогового имени (без дублей у вещей).
- Операции с тегами не пишутся в историю.

### 6.4. Статусы
- Раздел «Статусы»: список, создание, переименование, архивация и возврат из архива. Архивные показываются по переключателю «Показать архивные».
- Архивный статус не предлагается при выборе для новых назначений, но у вещей, которые его уже имеют, остаётся. В фильтре галереи архивные статусы доступны (иначе вещи с ними нельзя отфильтровать).
- Названия статусов уникальны без учёта регистра (среди всех, включая архивные).
- Если архивируется статус, который задан как «по умолчанию», «при передаче» или «при возврате», приложение требует выбрать другой.
- Физического удаления нет. Особой логики у статусов нет.

### 6.5. Люди
- Раздел «Люди»: создание, редактирование (имя, телефон, заметка), архивация и возврат из архива.
- Предупреждение при создании человека с уже существующим именем (без учёта регистра); сохранить дубль можно по явному подтверждению.
- Архивный человек не предлагается в новых передачах, но остаётся в истории и в поиске по имени.
- Физического удаления нет. Записи истории ссылаются на человека по id, поэтому переименование отражается везде.
- На карточке человека показывается список его передач и возвратов (вещь, дата, тип) со ссылкой на вещь.

### 6.6. Передачи и возвраты
Доступны из меню «Действия» на карточке вещи.

**Передать** (одна транзакция):
1. Обязательно выбрать человека из списка или создать нового прямо в диалоге.
2. Необязательный комментарий. В поле показывается подсказка: «Если отдаёте часть количества, укажите это в комментарии, например: отдал 2 шт.».
3. Флажок «Сменить статус на …» (включён по умолчанию, предлагается статус из `transfer_status_id`, можно выбрать другой или отключить).
4. Флажок «Снять место» (включён по умолчанию, можно отключить).
5. Результат: запись в `transfers` (kind = `give`), при включённом флажке запись в `status_changes` и смена статуса, при включённом флажке `place_id = NULL`.

**Вернуть** (одна транзакция):
1. Обязательно выбрать человека, от которого возвращается (по умолчанию предлагается последний, кому вещь передавалась).
2. Необязательный комментарий.
3. Выбор нового места (можно пропустить) и нового статуса (по умолчанию из `return_status_id`; можно оставить текущий).
4. Результат: запись в `transfers` (kind = `return`), при смене статуса запись в `status_changes`, обновление `place_id`.

Дата и время записей ставятся автоматически в момент действия.

### 6.7. История
- Раздел «История» на карточке вещи: единая лента смен статусов и передач/возвратов по датам, новые сверху. Показывается дата и время, тип события, детали (статус «было → стало», человек), комментарий.
- Записи не редактируются и не удаляются (ни через интерфейс, ни через код, ни напрямую: защита триггерами). Ошибки исправляются новой записью.
- Задним числом записать нельзя; реальную дату можно указать в комментарии.

### 6.8. Галерея
Режим 1, **сетка**:
- Квадратные превью с обрезкой по центру, под фото название; на плитке небольшая метка статуса.
- Ползунок размера плитки (мелко, средне, крупно), значение запоминается между запусками.
- Сортировка: по умолчанию новые сверху; доступны по названию и по дате добавления (с направлением).
- Фильтры: по месту (**включая вложенные места**; отдельный пункт «Без места»), по статусу (несколько, включая архивные), по тегам (несколько; вещь должна иметь все выбранные теги). Последние выбранные фильтры, сортировка и режим запоминаются между запусками, есть кнопка «Сбросить фильтры».
- Все вещи показываются всегда, скрытия по статусу нет.
- Превью загружаются лениво; на нескольких сотнях вещей прокрутка плавная.

Режим 2, **«По местам»**:
- Навигация внутрь места: показываются вложенные места (с фото) и вещи этого места. Сверху хлебные крошки, клик по сегменту ведёт на этот уровень.
- Первым в корне идёт виртуальный раздел «Без места» (вещи без места), вне алфавитного порядка.
- Порядок: сначала вложенные места, затем вещи; внутри групп по названию без учёта регистра с естественным порядком чисел («Полка 2» раньше «Полка 10»).
- Из этого режима создаются места («Добавить место») и вещи (с предзаполненным местом).

### 6.9. Карточка вещи (правая панель)
- Крупное фото целиком (без обрезки), название, описание, заметки, теги, количество.
- Путь к месту в виде кликабельных хлебных крошек: клик открывает это место в режиме «По местам».
- Текущий статус и быстрая смена статуса (диалог с необязательным комментарием).
- Раздел «История».
- Меню «Действия»: «Сменить статус», «Передать», «Вернуть», «Редактировать». Перемещение вещи делается через редактирование места.

## 7. Интерфейс

- Слева боковая панель: «Галерея», «По местам», «Люди», «Статусы», «Теги», «Данные».
- Сверху всегда видна строка поиска. Cmd+K переводит фокус в неё из любого места. Результаты поиска показываются в основной области в виде сетки (те же плитки; фильтры применяются и к поиску).
- Карточка вещи открывается в правой панели, без ухода с текущего экрана.
- Создание и редактирование вещи и места идут в модальном окне.
- Горячие клавиши: Cmd+K, Cmd+N (новая вещь), Cmd+W, Esc (закрыть окно или панель), стандартные меню macOS (в том числе «Настройки…»). Других горячих клавиш и контекстного меню нет.
- Светлая и тёмная тема следуют системной настройке.
- Только русский язык, строки в ARB.
- Разделы «Данные» и «Настройки…» (из меню приложения): см. раздел 10.
- Понятные сообщения об ошибках на русском; технические детали в лог.

## 8. Поиск

### 8.1. Что ищется
По одной строке запроса ищется по полям вещи: название, описание, заметки, теги; плюс название места и названия его родительских мест (допущение: запрос «шкаф» находит вещи на полках этого шкафа); плюс имена людей, которым вещь передавалась или от которых возвращалась (включая архивных).

### 8.2. Реализация
- Только на стороне Dart, без расширений SQLite. На объёме в сотни вещей индекс строится в памяти при запуске и точечно обновляется при изменениях.
- Нормализация: нижний регистр, ё→е, удаление пунктуации.
- Токенизация, русский стемминг (Snowball), для латиницы английский стемминг или без стемминга.
- Совпадения: по основе слова, по префиксу, а также нечёткие: расстояние Дамерау-Левенштейна с порогом, зависящим от длины слова, и/или сходство по триграммам.
- Ранжирование: точное совпадение выше стемминга, выше нечёткого; совпадение в названии весомее, чем в описании и заметках. Несколько слов в запросе объединяются по «И».
- Пустой запрос возвращает все вещи (как галерея).
- Допустимые параметры порогов агент подбирает сам, чтобы выполнялись критерии ниже без заметного количества ложных срабатываний.

### 8.3. Критерии приёмки поиска (обязательные тесты)
- «куртка» находит вещи с «куртки», «куртку» и «курточку».
- «курка» находит «куртка» (опечатка).
- «шкаф» находит вещь, лежащую в «Шкаф / Верхняя полка».
- Запрос по имени человека находит вещи, которые ему передавались, включая архивного человека.
- Запрос «ёлка» находит «елка» и наоборот.
- Неродственные слова не находятся (набор негативных тестов).
- Результат поиска на 500 вещах появляется менее чем за 100 мс.

## 9. Фото

### 9.1. Источники
1. Диалог выбора файла.
2. Перетаскивание файла в окно приложения (область фото в форме или окно создания).
3. Вставка из буфера обмена (Cmd+V в форме вещи или места).

Слой работы с фото проектируется расширяемым: новые источники (камера, Continuity Camera) добавляются без изменения остального кода.

### 9.2. Форматы и обработка
- Принимаются JPEG, PNG, HEIC/HEIF, WebP. Остальные файлы отклоняются сообщением «Формат не поддерживается».
- Предел по разрешению: 12 000 px по длинной стороне; при превышении показывается сообщение, приложение не зависает.
- Применяется ориентация по EXIF.
- Сохраняется копия в JPEG: длинная сторона не более 2 560 px, качество около 90 %. Прозрачность заменяется белым фоном.
- Превью: около 400 px по длинной стороне, JPEG.
- Исходный файл не изменяется и не удаляется.
- Каждая вещь и место получают собственную копию (без дедупликации).
- Имена файлов: `photos/<uuid>.jpg`, `thumbs/<uuid>.jpg`.
- При замене фото прежние файлы удаляются после успешной записи в базу.
- Декодирование и ресайз выполняются вне основного потока интерфейса (isolate или нативный код).

### 9.3. Надёжность
Порядок операций: сначала файлы, потом запись в базу. Если база не записалась, новые файлы удаляются. При запуске файлы-сироты (не упомянутые в базе) удаляются.

## 10. Хранилище, бэкап, импорт

### 10.1. Папка данных
- По умолчанию `~/Library/Application Support/Inventory/`.
- В настройках можно выбрать другую папку. При смене приложение предлагает перенести текущие данные или открыть уже существующее хранилище.
- Если выбрана папка в iCloud Drive, Dropbox, Google Drive, OneDrive (определение по пути, эвристика), показывается предупреждение: облако может повредить базу при синхронизации, одновременная работа с двух устройств не поддерживается, бэкап остаётся главной защитой.
- Одно хранилище нельзя открыть двумя экземплярами: блокировка при запуске (файловая блокировка ОС; устаревшие блокировки не мешают запуску).
- Если папка недоступна (например, отключён диск), приложение сообщает об этом и предлагает выбрать другую папку или повторить; пустую базу молча не создаёт.

### 10.2. Целостность и сбои
- Все записи идут в транзакциях; многошаговые операции (передача, возврат, объединение тегов, перенос данных) выполняются одной транзакцией.
- При запуске выполняется `PRAGMA integrity_check`. Если база повреждена, приложение сообщает об этом и предлагает восстановиться из ручного бэкапа; пустую базу не создаёт.
- Ошибки: понятное сообщение на русском пользователю, подробности в `logs/app.log` (ротация, например 5 файлов по 1 МБ).
- Напоминание о бэкапе, если последний экспорт был более 30 дней назад (или его не было); отключается в настройках.

### 10.3. Экспорт
- Раздел «Данные» → «Экспорт»: пользователь выбирает место, создаётся файл `Inventory-YYYY-MM-DD.inventory.zip`.
- Содержимое архива:
  - `manifest.json`: `format_version` (целое, начиная с 1), `app_version`, `exported_at`, количество записей по таблицам;
  - `data.json`: все таблицы (места, статусы, люди, вещи, теги, связи, история статусов, история передач, настройки) в читаемом виде;
  - `photos/`, `thumbs/`: файлы изображений.
- Экспорт не должен блокировать интерфейс; показывается прогресс.
- Данные из `_safety/` в архив не входят.

### 10.4. Импорт
- Раздел «Данные» → «Импорт»: выбор файла `.inventory.zip`.
- Проверки перед заменой: корректный zip, наличие и валидность `manifest.json`, `format_version` не выше поддерживаемой (иначе сообщение «Архив создан более новой версией»), ссылочная целостность (все связи и файлы фото на месте), совпадение числа записей с манифестом.
- Импорт **полностью заменяет** текущие данные. Перед заменой показывается предупреждение с описанием (сколько вещей будет заменено) и требуется подтверждение.
- Перед заменой автоматически создаётся копия текущего хранилища в `_safety/before-import/` (одна последняя копия).
- Если импорт не удался, данные автоматически возвращаются из копии и показывается сообщение об ошибке.
- Кнопка «Откатить последний импорт» доступна, пока копия существует.
- Миграции формата: код импорта должен уметь читать все прежние `format_version`.

### 10.5. Миграции базы
- Схема версионируется (drift).
- При запуске новой сборки, требующей миграции, файл базы копируется в `_safety/before-migration/` (одна последняя копия, фото не копируются).
- Если миграция не удалась, база возвращается из копии, показывается сообщение; приложение не работает на частично мигрированной базе.
- Откат миграции вручную (инструкция в README), так как откат без отката кода бессмыслен.

### 10.6. Копии безопасности
В разделе «Данные» показываются размер `_safety/` и кнопка «Удалить копии безопасности».

### 10.7. Настройки
Окно «Настройки…»: папка данных; статус по умолчанию для новых вещей; статус, предлагаемый при передаче; статус, предлагаемый при возврате; включить или отключить напоминание о бэкапе.

## 11. Нефункциональные требования

- Платформа: macOS 12 и новее, Apple Silicon и Intel (по умолчанию Flutter). App Sandbox отключён (`com.apple.security.app-sandbox = false`), чтобы работать с произвольной папкой данных.
- Производительность: запуск менее 3 с при 500 вещах; прокрутка галереи без заметных подвисаний; открытие карточки менее 200 мс.
- Надёжность: см. 10.2. Ни одно действие не должно оставлять базу в частично записанном состоянии.
- Приватность: данные не покидают устройство, никакой телеметрии и сетевых запросов.
- Код: статический анализ без предупреждений (`flutter analyze`), форматирование `dart format`.
- Поддерживаемость: бизнес-логика только в `inventory_core`, UI не обращается к базе напрямую.
- Доступность: поддержка масштабирования шрифта и фокуса с клавиатуры в диалогах (базовая).

## 12. Этапы разработки и критерии приёмки

После каждого этапа агент присылает: краткий отчёт, инструкцию проверки, результат запуска тестов, список отклонений от ТЗ. Следующий этап начинается после подтверждения.

### Этап 1. Каркас, база, иерархия мест
Объём: структура проекта (`inventory_core` и `app`), drift-схема со всеми таблицами и триггерами, создание хранилища (папка, блокировка, начальные статусы и настройки), миграции и копия перед миграцией, логирование, боковая панель, тема, локализация, режим «По местам» (только места), создание, редактирование, перемещение и удаление мест, фото места (пока через диалог выбора файла).

Приёмка:
- Приложение запускается из `flutter run -d macos`, создаёт хранилище.
- Место создаётся, редактируется, перемещается; хлебные крошки работают.
- Цикл в иерархии невозможен (тест и ручная проверка).
- Непустое место не удаляется, причина показана.
- Триггеры истории блокируют UPDATE/DELETE (тест).
- Второй экземпляр приложения с тем же хранилищем не запускается.
- Тесты `inventory_core` проходят.

### Этап 2. Вещи, фото, галерея
Объём: вещи (создание, редактирование, карточка), теги на вещи с автодополнением, все три источника фото, обработка (HEIC, EXIF, ресайз, превью, откат при сбое), очистка сирот, галерея-сетка (размер плиток, сортировки), «По местам» с вещами и «Без места», хлебные крошки на карточке, фильтры по месту, статусу и тегам с запоминанием.

Приёмка:
- Вещь без фото не сохраняется.
- JPEG, PNG, HEIC, WebP добавляются; неподдерживаемый формат даёт сообщение.
- Drag and drop и Cmd+V работают.
- Фото с поворотом EXIF отображаются правильно.
- Галерея на 500 тестовых вещах (скрипт генерации) прокручивается плавно.
- Фильтр по месту учитывает вложенные места; «Без места» работает.
- Тесты фото-пайплайна (в том числе откат при сбое записи в базу).

### Этап 3. Статусы, люди, история, передачи
Объём: разделы «Статусы», «Люди», «Теги» (переименование, удаление, объединение); смена статуса с комментарием; передача и возврат (транзакции); история на карточке; метка статуса на плитках; настройки статусов по умолчанию.

Приёмка:
- Список статусов по умолчанию создан; архивация и возврат работают; архивный статус не предлагается, но у вещей остаётся.
- «Передать» и «Вернуть» работают как описано в 6.6; при ошибке посреди операции ничего не сохраняется (тест).
- История неизменяема (тест, включая попытку прямого SQL).
- Дубль имени человека вызывает предупреждение; архивный человек не предлагается.
- Объединение тегов не создаёт дублей (тест).

### Этап 4. Поиск
Объём: индекс, нормализация, стемминг, нечёткий поиск, ранжирование, строка поиска и Cmd+K, результаты как плитки с фильтрами.

Приёмка: все примеры из 8.3; скорость менее 100 мс на 500 вещах; индекс обновляется после изменений вещи, места, тегов и людей без перезапуска.

### Этап 5. Бэкап, импорт, настройки, финализация
Объём: экспорт, импорт, откат импорта, автокопии, проверка целостности при запуске, смена папки данных, предупреждение об облаке, напоминание о бэкапе, окно настроек, README.

Приёмка:
- Round-trip: экспорт → импорт в чистое хранилище даёт идентичные данные и работающие фото (тест).
- Битый архив, архив с новой `format_version`, архив с отсутствующими фото отклоняются с понятным сообщением, данные не меняются.
- Сбой во время импорта возвращает прежние данные (тест с имитацией ошибки).
- «Откатить последний импорт» восстанавливает данные.
- Повреждённая база при запуске не приводит к созданию пустой базы.
- Отключённая папка данных обрабатывается корректно.
- `flutter build macos --release` создаёт рабочее `.app`.

## 13. Тесты (обязательный минимум)

Автотесты пишутся и запускаются на каждом этапе (`dart test` для ядра, `flutter test` для UI, один интеграционный smoke-тест на macOS к концу этапа 5).

- Иерархия мест: цикл, перемещение поддерева, удаление пустого и непустого места.
- Вещи: валидации, количество ≥ 1, обязательность фото, смена статуса на тот же запрещена.
- Транзакции передачи и возврата, откат при сбое.
- Неизменяемость истории.
- Теги: нормализация, переименование, объединение, автоудаление.
- Статусы и люди: архивация, ограничения.
- Поиск: примеры из 8.3, негативные тесты, производительность.
- Экспорт и импорт: round-trip, невалидные архивы, откат.
- Миграции: из каждой предыдущей версии схемы (начиная со второй версии).
- Фото: ориентация, ресайз, превью, откат файлов при сбое.
