## Задача

Проверить справочники, неизменяемую историю и атомарные операции.

## Что предоставить модели

Эту карточку целиком; утверждённые части API_CONTRACT.md и DECISIONS_APPROVED.md для перечисленных модулей; текущие интерфейсы/реализации и тесты только из области изменений; последний HANDOFF.md. Прочитать результат зависимостей по существующему коду, а не сочинять его по описанию. Если код или утверждённый контракт не приложен и недоступен через инструменты, вернуть BLOCKED с точным списком нужных файлов.

## Границы выполнения

Выполни только эту задачу. Не начинай следующую, не переписывай соседние модули и не меняй публичные контракты. Не добавляй функции вне MVP. Имена и папки в области изменений уточняются утверждённым API_CONTRACT.md; не создавай параллельную реализацию уже существующего сервиса. Если контракт противоречит ТЗ или требуется новое решение, останови зависимую часть и верни BLOCKED с причиной; не принимай решение молча.

## Сделать

1. Запустить согласованные тесты/анализ/форматирование
2. Повторить прямые SQL UPDATE/DELETE истории и fault-injection передач/возвратов
3. Пройти весь §12 этап 3, включая архивные сущности и merge tags
4. Зафиксировать отчёт, отклонения и получить подтверждение этапа

## Готово, когда

- Триггеры работают и после обновлений схемы

## Рабочий контекст

> Ниже — предложения для утверждённого контракта, а не замена исходного ТЗ. При расхождении сначала согласовать контракт.

### Общие границы

Это проект Inventory: одно локальное macOS-приложение, Flutter/Dart + SQLite, русский UI. inventory_core — чистый Dart: без package:flutter и dart:ui. UI обращается к сервисам ядра, а не к SQL. UUID v4 — строки; время — UTC Unix milliseconds, отображение локальное. Clock и IdGenerator внедряются для тестов. Все записи БД транзакционны, foreign_keys включается на каждом соединении. Исключённые функции из §2.2 не добавлять. У вещей и мест ровно одно обязательное фото. Вещи, статусы и люди физически не удаляются. Перед реализацией должен существовать утверждённый API_CONTRACT.md; имена ниже — предложения для его подготовки, а не повод менять уже согласованный API.

### Статусы, люди и история

StatusService и PeopleService не имеют физического удаления. Архивные статусы нельзя назначать заново; в текущих вещах и фильтре они остаются. Имена статусов уникальны без учёта регистра, включая архивные; не полагаться на ASCII NOCASE для кириллицы. Дубли имён людей допустимы после явного подтверждения. ItemActions.changeStatus / give / returnItem записывают историю и изменения вещи в одной транзакции. Дата только из Clock, не из формы; количество не меняется. UPDATE/DELETE для status_changes и transfers запрещены триггерами. Переименование статуса/человека отображается в старой истории через текущую связь по id. Флажок give «снять место» по умолчанию true. Пограничные случаи определены решениями D02–D04, D07, D08.

### Вещи, теги и галерея

ItemService: create / updateDetails / get / list; отдельного delete нет. Create выбирает активный default_status_id и не создаёт историю. UpdateDetails не принимает statusId: статус меняется отдельной командой. quantity — integer ≥1; название ≤200; photo обязателен; placeId nullable. TagKey = trim → collapse spaces → lower → ё/е; первое написание хранится в name, длина ≤50. Вещь имеет каждый тег не более одного раза; неиспользуемые теги удаляются после успешной операции. GalleryQuery: текст, место с потомками или «Без места», множество статусов включая архивные, все выбранные теги (AND), сортировка и направление. Фильтры применяются также к поиску.

### Интерфейс

Слева: Галерея / По местам / Люди / Статусы / Теги / Данные. Поиск всегда сверху; карточка вещи справа, формы модальные. Строки UI и перевод доменных ошибок — в русском ARB; технические детали в лог. Светлая/тёмная тема системные, базовые фокус клавиатуры и масштабирование текста. Разрешены Cmd+K, Cmd+N, Cmd+W, Esc, стандартные меню macOS; Cmd+V работает как источник фото в форме. Новых хоткеев и контекстного меню не добавлять. UI-настройки в PreferencesStore, настройки default/transfer/return_status_id — в таблице settings. Длительные операции показывают прогресс и не блокируют UI.

## 12. Критерии текущего этапа (выдержка)

### Этап 3. Статусы, люди, история, передачи
Объём: разделы «Статусы», «Люди», «Теги» (переименование, удаление, объединение); смена статуса с комментарием; передача и возврат (транзакции); история на карточке; метка статуса на плитках; настройки статусов по умолчанию.

Приёмка:
- Список статусов по умолчанию создан; архивация и возврат работают; архивный статус не предлагается, но у вещей остаётся.
- «Передать» и «Вернуть» работают как описано в 6.6; при ошибке посреди операции ничего не сохраняется (тест).
- История неизменяема (тест, включая попытку прямого SQL).
- Дубль имени человека вызывает предупреждение; архивный человек не предлагается.
- Объединение тегов не создаёт дублей (тест).

## 13. Тесты (обязательный минимум)

Автотесты пишутся и запускаются на каждом этапе (`dart test` для ядра, `flutter test` для UI, один интеграционный smoke-тест на macOS к концу этапа 5).

- Иерархия мест: цикл, перемещение поддерева, удаление пустого и непустого места.
- Вещи: валидации, количество ≥ 1, обязательность фото, смена статуса на тот же запрещена.
- Транзакции передачи и возврата, откат при сбое.
- Неизменяемость истории.
- Теги: нормализация, переименование, объединение, автоудаление.
- Статусы и люди: архивация, ограничения.
- Поиск: примеры из 8.3, негативные тесты, производительность.
- Экспорт и импорт: round-trip, невалидные архивы, откат.
- Миграции: из каждой предыдущей версии схемы (начиная со второй версии).
- Фото: ориентация, ресайз, превью, откат файлов при сбое.
