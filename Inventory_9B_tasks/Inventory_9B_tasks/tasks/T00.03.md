## Рабочий контекст

> Ниже — предложения для утверждённого контракта, а не замена исходного ТЗ. При расхождении сначала согласовать контракт.

### Общие границы

Это проект Inventory: одно локальное macOS-приложение, Flutter/Dart + SQLite, русский UI. inventory_core — чистый Dart: без package:flutter и dart:ui. UI обращается к сервисам ядра, а не к SQL. UUID v4 — строки; время — UTC Unix milliseconds, отображение локальное. Clock и IdGenerator внедряются для тестов. Все записи БД транзакционны, foreign_keys включается на каждом соединении. Исключённые функции из §2.2 не добавлять. У вещей и мест ровно одно обязательное фото. Вещи, статусы и люди физически не удаляются. Перед реализацией должен существовать утверждённый API_CONTRACT.md; имена ниже — предложения для его подготовки, а не повод менять уже согласованный API.

### Хранилище и жизненный цикл

StorageSession владеет БД и блокировкой одной канонической папки; повторное открытие того же пути запрещено ОС. StorageCoordinator различает createNew / openExisting / migrate / switch / import; отсутствие ожидаемой папки не означает создание пустой базы. StoreLayout: inventory.db, photos/, thumbs/, logs/, _safety/. Путь активной папки и UI-настройки хранятся вне папки, в адаптере PreferencesStore. integrity_check выполняется до рабочих запросов и очистки файлов. При потенциальной миграции копия согласованной базы создаётся ДО запуска мигратора drift. Снимок SQLite учитывает WAL: произвольное копирование открытого inventory.db недостаточно. Семантика переключений и восстановления утверждается в решении D01.

### Фотографии

ImageProcessor — порт ядра; macOS-реализация в app/platform. Вход: bytes или выбранный файл без изменения оригинала. Выход PreparedPhoto: новые относительные photo_file/thumb_file, размеры и служебные сведения для отката. Форматы JPEG/PNG/WebP/HEIC/HEIF, длинная сторона входа ≤12000 px. EXIF применяется до ресайза; JPEG ≤2560 px, качество около 90%, белый фон вместо alpha; thumbnail около 400 px. Имена photos/<uuid>.jpg и thumbs/<uuid>.jpg, копии отдельные для каждого владельца. Новый комплект записывается до SQL; при сбое SQL удаляется; старый удаляется только после commit. Декодирование вне UI-потока. При аварии до уборки сироты устраняются при следующем безопасном запуске.

### Места

PlaceService: create / update / move / deleteEmpty / path / descendants / children. Конкретные DTO утверждаются в T00.03. name обязателен, ≤200 символов, parentId nullable. Путь вычисляется из иерархии. Дубли у одного родителя разрешены после предупреждения. Нельзя выбрать самого себя или потомка; сервером здесь является доменный сервис, UI-фильтра недостаточно. Удаление запрещено при прямых детях или вещах; ошибка содержит оба числа. Перенос сохраняет всё поддерево без изменения его id. После успешного удаления пустого места убирается его собственная пара фото. Естественная сортировка: «Полка 2» перед «Полка 10».

### Вещи, теги и галерея

ItemService: create / updateDetails / get / list; отдельного delete нет. Create выбирает активный default_status_id и не создаёт историю. UpdateDetails не принимает statusId: статус меняется отдельной командой. quantity — integer ≥1; название ≤200; photo обязателен; placeId nullable. TagKey = trim → collapse spaces → lower → ё/е; первое написание хранится в name, длина ≤50. Вещь имеет каждый тег не более одного раза; неиспользуемые теги удаляются после успешной операции. GalleryQuery: текст, место с потомками или «Без места», множество статусов включая архивные, все выбранные теги (AND), сортировка и направление. Фильтры применяются также к поиску.

### Статусы, люди и история

StatusService и PeopleService не имеют физического удаления. Архивные статусы нельзя назначать заново; в текущих вещах и фильтре они остаются. Имена статусов уникальны без учёта регистра, включая архивные; не полагаться на ASCII NOCASE для кириллицы. Дубли имён людей допустимы после явного подтверждения. ItemActions.changeStatus / give / returnItem записывают историю и изменения вещи в одной транзакции. Дата только из Clock, не из формы; количество не меняется. UPDATE/DELETE для status_changes и transfers запрещены триггерами. Переименование статуса/человека отображается в старой истории через текущую связь по id. Флажок give «снять место» по умолчанию true. Пограничные случаи определены решениями D02–D04, D07, D08.

### Поиск

SearchDocument хранит itemId и поля отдельно с указанием источника: name, description, notes, tags, названия текущего места и всех его предков, имена всех людей из give/return, включая архивных. Индекс — в памяти в чистом Dart, без FTS/нативных токенизаторов SQLite. Нормализация lower + ё/е + пунктуация, русский Snowball, латиница согласно T00.02. SearchEngine.search(query) возвращает ранжированные itemId; несколько слов = AND, пустой запрос = все вещи. Точное совпадение выше стемминга и нечёткого, название весомее описания/заметок. Префикс и Дамерау–Левенштейн/триграммы реализуются по фиксированным правилам D05. Результат пересекается с GalleryQuery. После commit сервис публикует MutationEvent, индекс обновляется с учётом зависимых вещей.

### Архив и безопасная замена

BackupCodec v1: manifest.json(format_version=1, app_version, exported_at, counts), data.json со всеми 9 таблицами, photos/, thumbs/. Не включать _safety/, logs/, preferences, lock-файлы. «9 таблиц» = places, statuses, people, items, tags, item_tags, status_changes, transfers, settings. BackupValidator не меняет активные данные. ValidatedBackup — только проверенный staging. Импорт: полная проверка → подтверждение числа вещей → последняя safety-копия → остановка операций → подготовленная замена → проверка/открытие → возобновление. При сбое восстановить старое состояние. Временные папки и журнал не смешивать с _safety; до успешной замены прежнюю копию не уничтожать. SQL-транзакция не покрывает файловую систему: соблюдать утверждённый D01. Импортировать историю INSERT в новую staging-БД с работающими триггерами, а не DELETE из живой истории.

### Интерфейс

Слева: Галерея / По местам / Люди / Статусы / Теги / Данные. Поиск всегда сверху; карточка вещи справа, формы модальные. Строки UI и перевод доменных ошибок — в русском ARB; технические детали в лог. Светлая/тёмная тема системные, базовые фокус клавиатуры и масштабирование текста. Разрешены Cmd+K, Cmd+N, Cmd+W, Esc, стандартные меню macOS; Cmd+V работает как источник фото в форме. Новых хоткеев и контекстного меню не добавлять. UI-настройки в PreferencesStore, настройки default/transfer/return_status_id — в таблице settings. Длительные операции показывают прогресс и не блокируют UI.

## 5. Модель данных

Идентификаторы: UUID v4 (текст). Время: целое число, Unix time в миллисекундах UTC; в интерфейсе показывается в локальном часовом поясе.

```sql
CREATE TABLE places (
  id TEXT PRIMARY KEY,
  parent_id TEXT REFERENCES places(id) ON DELETE RESTRICT,   -- NULL = корневое
  name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  photo_file TEXT NOT NULL,        -- относительный путь, photos/...
  thumb_file TEXT NOT NULL,        -- thumbs/...
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE statuses (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  is_archived INTEGER NOT NULL DEFAULT 0,
  sort_order INTEGER NOT NULL,     -- порядок создания
  created_at INTEGER NOT NULL
);

CREATE TABLE people (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  phone TEXT NOT NULL DEFAULT '',
  notes TEXT NOT NULL DEFAULT '',
  is_archived INTEGER NOT NULL DEFAULT 0,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE items (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  notes TEXT NOT NULL DEFAULT '',
  quantity INTEGER NOT NULL DEFAULT 1 CHECK (quantity >= 1),
  place_id TEXT REFERENCES places(id) ON DELETE RESTRICT,    -- NULL = «Без места»
  status_id TEXT NOT NULL REFERENCES statuses(id) ON DELETE RESTRICT,
  photo_file TEXT NOT NULL,
  thumb_file TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE TABLE tags (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,              -- как введено первым
  name_key TEXT NOT NULL UNIQUE    -- нормализовано: trim, схлопнутые пробелы, нижний регистр, ё→е
);

CREATE TABLE item_tags (
  item_id TEXT NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  tag_id TEXT NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (item_id, tag_id)
);

CREATE TABLE status_changes (      -- неизменяемая
  id TEXT PRIMARY KEY,
  item_id TEXT NOT NULL REFERENCES items(id) ON DELETE RESTRICT,
  from_status_id TEXT NOT NULL REFERENCES statuses(id) ON DELETE RESTRICT,
  to_status_id TEXT NOT NULL REFERENCES statuses(id) ON DELETE RESTRICT,
  comment TEXT NOT NULL DEFAULT '',
  created_at INTEGER NOT NULL
);

CREATE TABLE transfers (           -- неизменяемая
  id TEXT PRIMARY KEY,
  item_id TEXT NOT NULL REFERENCES items(id) ON DELETE RESTRICT,
  kind TEXT NOT NULL CHECK (kind IN ('give','return')),
  person_id TEXT NOT NULL REFERENCES people(id) ON DELETE RESTRICT,
  comment TEXT NOT NULL DEFAULT '',
  created_at INTEGER NOT NULL
);

CREATE TABLE settings (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
-- ключи: default_status_id, transfer_status_id, return_status_id
```

Триггеры неизменяемости:
```sql
CREATE TRIGGER status_changes_no_update BEFORE UPDATE ON status_changes
BEGIN SELECT RAISE(ABORT, 'history is immutable'); END;
CREATE TRIGGER status_changes_no_delete BEFORE DELETE ON status_changes
BEGIN SELECT RAISE(ABORT, 'history is immutable'); END;
-- то же для transfers
```

Индексы: `items(place_id)`, `items(status_id)`, `places(parent_id)`, `item_tags(tag_id)`, `status_changes(item_id, created_at)`, `transfers(item_id, created_at)`, `transfers(person_id)`.

Включить `PRAGMA foreign_keys = ON` для каждого соединения.

Начальные данные при создании нового хранилища (один раз): статусы «В наличии», «Одолжил», «Отдал», «Продал», «Выбросил», «Потерял», «В ремонте». Настройки: `default_status_id` = «В наличии», `transfer_status_id` = «Отдал», `return_status_id` = «В наличии».

### 9.3. Надёжность
Порядок операций: сначала файлы, потом запись в базу. Если база не записалась, новые файлы удаляются. При запуске файлы-сироты (не упомянутые в базе) удаляются.

### 10.2. Целостность и сбои
- Все записи идут в транзакциях; многошаговые операции (передача, возврат, объединение тегов, перенос данных) выполняются одной транзакцией.
- При запуске выполняется `PRAGMA integrity_check`. Если база повреждена, приложение сообщает об этом и предлагает восстановиться из ручного бэкапа; пустую базу не создаёт.
- Ошибки: понятное сообщение на русском пользователю, подробности в `logs/app.log` (ротация, например 5 файлов по 1 МБ).
- Напоминание о бэкапе, если последний экспорт был более 30 дней назад (или его не было); отключается в настройках.

### 10.4. Импорт
- Раздел «Данные» → «Импорт»: выбор файла `.inventory.zip`.
- Проверки перед заменой: корректный zip, наличие и валидность `manifest.json`, `format_version` не выше поддерживаемой (иначе сообщение «Архив создан более новой версией»), ссылочная целостность (все связи и файлы фото на месте), совпадение числа записей с манифестом.
- Импорт **полностью заменяет** текущие данные. Перед заменой показывается предупреждение с описанием (сколько вещей будет заменено) и требуется подтверждение.
- Перед заменой автоматически создаётся копия текущего хранилища в `_safety/before-import/` (одна последняя копия).
- Если импорт не удался, данные автоматически возвращаются из копии и показывается сообщение об ошибке.
- Кнопка «Откатить последний импорт» доступна, пока копия существует.
- Миграции формата: код импорта должен уметь читать все прежние `format_version`.

## 12. Этапы разработки и критерии приёмки

После каждого этапа агент присылает: краткий отчёт, инструкцию проверки, результат запуска тестов, список отклонений от ТЗ. Следующий этап начинается после подтверждения.

### Этап 1. Каркас, база, иерархия мест
Объём: структура проекта (`inventory_core` и `app`), drift-схема со всеми таблицами и триггерами, создание хранилища (папка, блокировка, начальные статусы и настройки), миграции и копия перед миграцией, логирование, боковая панель, тема, локализация, режим «По местам» (только места), создание, редактирование, перемещение и удаление мест, фото места (пока через диалог выбора файла).

Приёмка:
- Приложение запускается из `flutter run -d macos`, создаёт хранилище.
- Место создаётся, редактируется, перемещается; хлебные крошки работают.
- Цикл в иерархии невозможен (тест и ручная проверка).
- Непустое место не удаляется, причина показана.
- Триггеры истории блокируют UPDATE/DELETE (тест).
- Второй экземпляр приложения с тем же хранилищем не запускается.
- Тесты `inventory_core` проходят.

### Этап 2. Вещи, фото, галерея
Объём: вещи (создание, редактирование, карточка), теги на вещи с автодополнением, все три источника фото, обработка (HEIC, EXIF, ресайз, превью, откат при сбое), очистка сирот, галерея-сетка (размер плиток, сортировки), «По местам» с вещами и «Без места», хлебные крошки на карточке, фильтры по месту, статусу и тегам с запоминанием.

Приёмка:
- Вещь без фото не сохраняется.
- JPEG, PNG, HEIC, WebP добавляются; неподдерживаемый формат даёт сообщение.
- Drag and drop и Cmd+V работают.
- Фото с поворотом EXIF отображаются правильно.
- Галерея на 500 тестовых вещах (скрипт генерации) прокручивается плавно.
- Фильтр по месту учитывает вложенные места; «Без места» работает.
- Тесты фото-пайплайна (в том числе откат при сбое записи в базу).

### Этап 3. Статусы, люди, история, передачи
Объём: разделы «Статусы», «Люди», «Теги» (переименование, удаление, объединение); смена статуса с комментарием; передача и возврат (транзакции); история на карточке; метка статуса на плитках; настройки статусов по умолчанию.

Приёмка:
- Список статусов по умолчанию создан; архивация и возврат работают; архивный статус не предлагается, но у вещей остаётся.
- «Передать» и «Вернуть» работают как описано в 6.6; при ошибке посреди операции ничего не сохраняется (тест).
- История неизменяема (тест, включая попытку прямого SQL).
- Дубль имени человека вызывает предупреждение; архивный человек не предлагается.
- Объединение тегов не создаёт дублей (тест).

### Этап 4. Поиск
Объём: индекс, нормализация, стемминг, нечёткий поиск, ранжирование, строка поиска и Cmd+K, результаты как плитки с фильтрами.

Приёмка: все примеры из 8.3; скорость менее 100 мс на 500 вещах; индекс обновляется после изменений вещи, места, тегов и людей без перезапуска.

### Этап 5. Бэкап, импорт, настройки, финализация
Объём: экспорт, импорт, откат импорта, автокопии, проверка целостности при запуске, смена папки данных, предупреждение об облаке, напоминание о бэкапе, окно настроек, README.

Приёмка:
- Round-trip: экспорт → импорт в чистое хранилище даёт идентичные данные и работающие фото (тест).
- Битый архив, архив с новой `format_version`, архив с отсутствующими фото отклоняются с понятным сообщением, данные не меняются.
- Сбой во время импорта возвращает прежние данные (тест с имитацией ошибки).
- «Откатить последний импорт» восстанавливает данные.
- Повреждённая база при запуске не приводит к созданию пустой базы.
- Отключённая папка данных обрабатывается корректно.
- `flutter build macos --release` создаёт рабочее `.app`.

## 17. Что агент должен сообщить до начала работы

Перед этапом 1 агент кратко подтверждает: выбранные пакеты Flutter (с обоснованием), способ декодирования HEIC, способ чтения изображений из буфера обмена, структуру проекта. При противоречиях в ТЗ или невозможности требования агент задаёт вопрос, а не принимает решение молча.

## Ответ исполнителя

Верни: DONE или BLOCKED; что изменено; список файлов; фактические команды проверки и их результат; что проверено вручную на Mac; отклонения от ТЗ и нерешённые вопросы. Не называй тесты пройденными, если их не запускал. Для кода добавь/обнови тесты бизнес-правил и отказов, перечисленных в этой карточке; не пиши тесты, просто повторяющие реализацию. Для документа/приёмки проверь содержимое и ссылки без бессмысленных unit-тестов. Обнови HANDOFF.md по шаблону и запись своей задачи в RUN_LOG.md. DONE — только после выполнения критериев; незапущенные обязательные проверки означают BLOCKED. На карточке приёмки этапа выполнение проверок не заменяет подтверждение владельца.
