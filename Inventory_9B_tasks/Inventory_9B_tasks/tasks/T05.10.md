# T05.10. Переносить текущие данные в другую папку

**Исполнитель:** 9B по утверждённому протоколу + обязательное ревью опытного разработчика.

**Зависимости:** [T05.09](T05.09.md), [T01.07](T01.07.md).

**Исходник:** §10.1, §10.2 [TZ_inventory_mvp.md](../00_SOURCE/TZ_inventory_mvp.md).

**Область изменений:** StorageMover; two-directory tests.

## Задача

Перенести согласованное хранилище без потери старого при сбое.

## Что предоставить модели

Эту карточку целиком; утверждённые части API_CONTRACT.md и DECISIONS_APPROVED.md для перечисленных модулей; текущие интерфейсы/реализации и тесты только из области изменений; последний HANDOFF.md. Прочитать результат зависимостей по существующему коду, а не сочинять его по описанию. Если код или утверждённый контракт не приложен и недоступен через инструменты, вернуть BLOCKED с точным списком нужных файлов.

## Границы выполнения

Выполни только эту задачу. Не начинай следующую, не переписывай соседние модули и не меняй публичные контракты. Не добавляй функции вне MVP. Имена и папки в области изменений уточняются утверждённым API_CONTRACT.md; не создавай параллельную реализацию уже существующего сервиса. Если контракт противоречит ТЗ или требуется новое решение, останови зависимую часть и верни BLOCKED с причиной; не принимай решение молча.

## Сделать

1. Проверить права и запретить опасные назначения: тот же путь/вложение/неявная перезапись чужого хранилища
2. Взять нужные locks, остановить операции, скопировать и проверить staging назначения
3. Переключить session и внешний saved path только после проверки
4. Старую папку удалять/оставлять только по D01, не рисковать единственной исправной копией
5. Перестроить индекс и сбросить устаревшие фильтры по D12

## Готово, когда

- Нехватка места и ошибка нового открытия сохраняют доступное прежнее хранилище
- Успешный перенос сохраняет все данные/фото и нужные safety-копии по D01
- Конкурирующий процесс блокирует перенос
- Перезапуск после обрыва восстанавливается по журналу

## Рабочий контекст

> Ниже — предложения для утверждённого контракта, а не замена исходного ТЗ. При расхождении сначала согласовать контракт.

### Общие границы

Это проект Inventory: одно локальное macOS-приложение, Flutter/Dart + SQLite, русский UI. inventory_core — чистый Dart: без package:flutter и dart:ui. UI обращается к сервисам ядра, а не к SQL. UUID v4 — строки; время — UTC Unix milliseconds, отображение локальное. Clock и IdGenerator внедряются для тестов. Все записи БД транзакционны, foreign_keys включается на каждом соединении. Исключённые функции из §2.2 не добавлять. У вещей и мест ровно одно обязательное фото. Вещи, статусы и люди физически не удаляются. Перед реализацией должен существовать утверждённый API_CONTRACT.md; имена ниже — предложения для его подготовки, а не повод менять уже согласованный API.

### Хранилище и жизненный цикл

StorageSession владеет БД и блокировкой одной канонической папки; повторное открытие того же пути запрещено ОС. StorageCoordinator различает createNew / openExisting / migrate / switch / import; отсутствие ожидаемой папки не означает создание пустой базы. StoreLayout: inventory.db, photos/, thumbs/, logs/, _safety/. Путь активной папки и UI-настройки хранятся вне папки, в адаптере PreferencesStore. integrity_check выполняется до рабочих запросов и очистки файлов. При потенциальной миграции копия согласованной базы создаётся ДО запуска мигратора drift. Снимок SQLite учитывает WAL: произвольное копирование открытого inventory.db недостаточно. Семантика переключений и восстановления утверждается в решении D01.

### Архив и безопасная замена

BackupCodec v1: manifest.json(format_version=1, app_version, exported_at, counts), data.json со всеми 9 таблицами, photos/, thumbs/. Не включать _safety/, logs/, preferences, lock-файлы. «9 таблиц» = places, statuses, people, items, tags, item_tags, status_changes, transfers, settings. BackupValidator не меняет активные данные. ValidatedBackup — только проверенный staging. Импорт: полная проверка → подтверждение числа вещей → последняя safety-копия → остановка операций → подготовленная замена → проверка/открытие → возобновление. При сбое восстановить старое состояние. Временные папки и журнал не смешивать с _safety; до успешной замены прежнюю копию не уничтожать. SQL-транзакция не покрывает файловую систему: соблюдать утверждённый D01. Импортировать историю INSERT в новую staging-БД с работающими триггерами, а не DELETE из живой истории.

### Поиск

SearchDocument хранит itemId и поля отдельно с указанием источника: name, description, notes, tags, названия текущего места и всех его предков, имена всех людей из give/return, включая архивных. Индекс — в памяти в чистом Dart, без FTS/нативных токенизаторов SQLite. Нормализация lower + ё/е + пунктуация, русский Snowball, латиница согласно T00.02. SearchEngine.search(query) возвращает ранжированные itemId; несколько слов = AND, пустой запрос = все вещи. Точное совпадение выше стемминга и нечёткого, название весомее описания/заметок. Префикс и Дамерау–Левенштейн/триграммы реализуются по фиксированным правилам D05. Результат пересекается с GalleryQuery. После commit сервис публикует MutationEvent, индекс обновляется с учётом зависимых вещей.

## Релевантные пункты исходного ТЗ

### 10.1. Папка данных
- По умолчанию `~/Library/Application Support/Inventory/`.
- В настройках можно выбрать другую папку. При смене приложение предлагает перенести текущие данные или открыть уже существующее хранилище.
- Если выбрана папка в iCloud Drive, Dropbox, Google Drive, OneDrive (определение по пути, эвристика), показывается предупреждение: облако может повредить базу при синхронизации, одновременная работа с двух устройств не поддерживается, бэкап остаётся главной защитой.
- Одно хранилище нельзя открыть двумя экземплярами: блокировка при запуске (файловая блокировка ОС; устаревшие блокировки не мешают запуску).
- Если папка недоступна (например, отключён диск), приложение сообщает об этом и предлагает выбрать другую папку или повторить; пустую базу молча не создаёт.

### 10.2. Целостность и сбои
- Все записи идут в транзакциях; многошаговые операции (передача, возврат, объединение тегов, перенос данных) выполняются одной транзакцией.
- При запуске выполняется `PRAGMA integrity_check`. Если база повреждена, приложение сообщает об этом и предлагает восстановиться из ручного бэкапа; пустую базу не создаёт.
- Ошибки: понятное сообщение на русском пользователю, подробности в `logs/app.log` (ротация, например 5 файлов по 1 МБ).
- Напоминание о бэкапе, если последний экспорт был более 30 дней назад (или его не было); отключается в настройках.
