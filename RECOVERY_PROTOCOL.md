# RECOVERY_PROTOCOL — безопасная замена данных и восстановление

Версия: 1.0
Дата: 14 ноября 2026
Основание: D01, T00.03, §9.3, §10.2, §10.4 ТЗ.
Область: миграция схемы, импорт, откат импорта, перенос папки данных, переключение хранилища. Этап 1 реализует блокировку, снимок и миграцию; остальные операции обязаны следовать этому документу начиная с этапа 5.

## 1. Главный принцип

SQLite-транзакция не покрывает файловую систему. Поэтому атомарность обеспечивается не одной SQL-транзакцией, а протоколом:

1. Эксклюзивная блокировка хранилища на всё время операции.
2. Согласованный снимок текущего состояния (SQLite — через `VACUUM INTO`; файлы — копированием при остановленных мутациях).
3. Подготовка нового состояния в staging.
4. Durable-журнал фаз в `_safety/recovery.json`.
5. Атомарные переименования в пределах одной файловой системы.
6. Проверка нового состояния.
7. Только после успеха — удаление временного; прежняя копия хранится до явного решения владельца.

Прерывание приложения на любом шаге не должно оставлять базу в состоянии, которое новый код молча примет за валидное. При сомнении — восстановление из снимка и явная ошибка.

## 2. Раскладка

```
<root>/
  inventory.db
  inventory.db-wal
  inventory.db-shm
  photos/
  thumbs/
  logs/
  .inventory.lock
  _safety/
    recovery.json            # журнал активной/последней операции
    before-migration/
      inventory.db           # один последний снимок ДО миграции
      meta.json
    before-import/
      inventory.db
      photos/
      thumbs/
      meta.json              # один последний снимок ДО импорта
  _tmp/
    import-<opId>/           # staging импорта
    old-<opId>/              # вынесенное старое при swap
    move-<opId>/             # staging переноса
```

Правила:
- `_safety` и `_tmp` не попадают в экспорт, не смешиваются с `photos`/`thumbs`, не удаляются очисткой сирот.
- `logs` не входят в снимки данных.
- В `_safety` хранится **одна** последняя копия каждого вида. Новая копия создаётся только после успешной проверки предыдущей операции; прежняя не уничтожается до успешного завершения новой.
- Пути в журнале — абсолютные канонические.

## 3. Блокировка

- Перед любой операцией берётся `StorageLock` на `<root>/.inventory.lock` (эксклюзивная ОС-блокировка, дескриптор открыт).
- Второй процесс получает `storage_busy`; существование файла само по себе не блокирует.
- Все пути канонизируются (`realpath`), поэтому `/a/../a` и симлинк ведут к одной блокировке.
- Блокировка удерживается до закрытия сессии/завершения восстановления.
- Внутри процесса на время операции включается режим обслуживания: новые мутации отклоняются, UI показывает прогресс. Открытые транзакции завершаются, затем выполняется снимок.

## 4. Согласованный снимок SQLite

Произвольное копирование `inventory.db` при включённом WAL недопустимо: часть данных находится в `-wal`.

Алгоритм `SqliteSnapshot.create(sourceDb, targetDb)`:

1. Открыть отдельное соединение к `sourceDb` (read/write).
2. `PRAGMA busy_timeout = 5000`.
3. `PRAGMA wal_checkpoint(FULL)` — перенести WAL в основной файл, не разрушая данные.
4. `VACUUM INTO '<targetDb>'` — создать согласованную копию без WAL.
5. Закрыть соединение; открыть копию, выполнить `PRAGMA integrity_check`; ошибка → удалить копию и прервать операцию.
6. `fsync` файла копии; `sync()` (см. §5).

Для файлов `photos/` и `thumbs/`: копирование только при активной блокировке и остановленных мутациях; файлы неизменяемы после записи, поэтому копия консистентна. Копия проверяется по количеству и наличию всех ссылок из снимка БД.

## 5. Durable-маркер и атомарная запись

- Журнал: `_safety/recovery.json`.
- Запись: `<file>.tmp` → `flush` + `fsync` → `rename` поверх `recovery.json`.
- После критических `rename` вызывается `sync()` через FFI (macOS `sync(2)`): это гарантирует сброс метаданных каталога. Без этого rename может быть потерян при отключении питания. Если `sync()` недоступен, операция продолжается, но в журнал пишется `durability: "best_effort"`; это отклонение фиксируется в отчёте.
- Журнал читается при каждом старте **до** открытия drift и до любых рабочих запросов.
- `recovery.json` содержит только одну активную операцию. Поле `phase` — единственный источник истины о прогрессе.

```json
{
  "protocol_version": 1,
  "operation": "import",
  "op_id": "8f0c…",
  "phase": "swap_started",
  "started_at": 1760000000000,
  "updated_at": 1760000000100,
  "root": "/Users/me/Library/Application Support/Inventory",
  "backup": "_safety/before-import",
  "staging": "_tmp/import-8f0c…",
  "target": null,
  "durability": "fsync",
  "details": {"items_count": 42}
}
```

Допустимые `operation`: `migration`, `import`, `import_rollback`, `move`, `switch`. Терминальная фаза — `done` или `rolled_back`; после неё журнал можно удалить, но копия остаётся по правилам операции.

## 6. Восстановление при старте

Порядок:

1. Взять `StorageLock` (без него — `storage_busy`, ничего не менять).
2. Прочитать `_safety/recovery.json`, если есть.
3. Если `phase == done` или `rolled_back` — удалить незавершённые `_tmp` этой операции, продолжить обычное открытие.
4. Иначе — выполнить восстановление по таблице §7.
5. Проверить `PRAGMA integrity_check`.
6. Только после успеха открыть drift. Любая ошибка восстановления → `storage_corrupt`/`migration_failed`, соединение закрыто, пустая БД не создаётся.
7. Записать результат в лог; журнал перевести в `rolled_back`.

Повторный запуск восстановления идемпотентен: копирование одного и того же снимка поверх текущего состояния даёт тот же результат.

## 7. Фазы и точки восстановления

### 7.1. Миграция схемы (`migration`)

| Фаза | Что уже сделано | Сбой/перезапуск |
|---|---|---|
| `started` | журнал создан | удалить `before-migration`, продолжить обычное открытие |
| `snapshot_done` | снимок ДО миграции готов | восстановить снимок, удалить журнал |
| `migrating` | drift выполняет `onUpgrade` | закрыть БД, восстановить снимок |
| `verify` | миграция завершена, идёт integrity_check | при ошибке восстановить снимок |
| `done` | новая схема проверена | удалить журнал, открыть рабочим кодом |

Правила:
- Снимок создаётся **до** вызова мигратора drift.
- Копируется только БД; `photos/`/`thumbs/` не трогаются (миграция схемы их не меняет).
- Если `user_version` в БД больше поддерживаемой — `storage_newer_schema`, без миграции и без изменений.
- При ошибке приложение не продолжает работать «новым кодом на старой схеме»: сессия не создаётся.

### 7.2. Импорт (`import`)

| Фаза | Durable-маркер | Сбой/перезапуск |
|---|---|---|
| `validating` | архив распакован в `_tmp/import-<id>`, проверяется | удалить staging, данные не менялись |
| `snapshot_done` | `_safety/before-import` содержит БД+photos+thumbs | удалить staging, продолжить работу |
| `staging_ready` | новая БД/фото проверены | удалить staging, старое не тронуто |
| `swap_started` | старые `photos/thumbs/db` переименованы в `_tmp/old-<id>`; новые на месте | восстановить `before-import` целиком |
| `verifying` | новый набор открыт, integrity_check | восстановить `before-import` |
| `done` | новый набор подтверждён | удалить `_tmp/old-<id>`, оставить `before-import` |

Дополнительно:
- Пользователь подтверждает число вещей до `snapshot_done`.
- После `swap_started` никакие пользовательские операции не выполняются.
- «Откат последнего импорта» доступен, пока существует `_safety/before-import` (см. 7.3).
- Ошибка удаления `_tmp/old-<id>` после `done` не откатывает импорт; логируется.

### 7.3. Откат импорта (`import_rollback`)

| Фаза | Что сделано | Сбой/перезапуск |
|---|---|---|
| `started` | пользователь подтвердил | — |
| `snapshot_done` | текущее состояние сохранено в `_safety/before-import-rollback` (для диагностики) | удалить, ничего не менялось |
| `restoring` | `before-import` копируется поверх текущего | повторить копирование (идемпотентно) |
| `verifying` | integrity_check | повторить восстановление |
| `rolled_back` | старое состояние возвращено | журнал закрыт; `before-import` остаётся |

Повторное нажатие «Откатить» при `rolled_back` либо недоступно, либо идемпотентно восстанавливает ту же копию. Данные не удаляются, пока владелец явно не удалит копию.

### 7.4. Перенос данных в другую папку (`move`)

| Фаза | Что сделано | Сбой/перезапуск |
|---|---|---|
| `started` | целевая папка проверена на пустоту/пригодность | удалить staging |
| `snapshot_done` | снимок БД источника | удалить staging |
| `copying` | БД+photos+thumbs копируются в `_tmp/move-<id>` | удалить staging, источник не тронут |
| `copied` | копия проверена (integrity_check, количество фото) | удалить staging |
| `switching` | `storage.active_path` переключён на целевую папку | если цель валидна — завершить; иначе вернуть прежний путь |
| `done` | приложение работает с новой папкой | старая папка остаётся |

Старая папка **не удаляется** автоматически. Владелец удаляет её вручную после проверки (T05.10).
Копирование выполняется при остановленных мутациях; источник блокируется до конца операции.

### 7.5. Переключение на существующее хранилище (`switch`)

- Взять блокировку новой папки, проверить `inventory.db`, integrity_check, версию схемы.
- При успехе обновить `storage.active_path`, закрыть старую сессию, открыть новую.
- При ошибке прежняя сессия и прежний путь остаются; новая папка не изменяется.
- Данные не копируются и не заменяются.

## 8. Таблица «шаг → сбой → восстановление» (сводно)

| Шаг | Сбой | Гарантия |
|---|---|---|
| Создание снимка | `VACUUM INTO`/integrity | копия удаляется, рабочее состояние не менялось |
| Запись журнала | fsync/rename | предыдущий журнал цел; операция не начинается |
| Staging | распаковка/валидация | staging удаляется, рабочее состояние не менялось |
| Swap | питание/авария | журнал `swap_started` → восстановление полного снимка |
| Проверка нового | integrity/открытие | восстановление снимка, ошибка пользователю |
| Удаление старого | нет прав/IO | успех сохраняется, warning в лог |
| Восстановление | повторный сбой | повтор идемпотентен; пустая БД не создаётся |

## 9. Ограничения и честные допущения

- `sync()` через FFI — системный вызов macOS; на других ОС протокол не проверялся (продукт только macOS).
- APFS-переименование в пределах одной папки атомарно; перенос между томами не используется для swap (только копирование + rename внутри целевой папки).
- Снимок `VACUUM INTO` требует свободного места не меньше размера БД; при нехватке — `storage_unavailable` с понятной причиной, рабочее состояние не меняется.
- Копия `before-import` включает фото и превью; это осознанно больше по размеру, зато откат восстанавливает и файлы.
- Внешние облачные синхронизаторы (iCloud/Dropbox) могут менять файлы вне блокировки; приложение предупреждает (этап 5), но не может это предотвратить.

## 10. Адаптация для Swift-версии (принято владельцем при переносе из ThingsMap2)

- Журнал, снимки, staging и восстановление реализованы в `Sources/InventoryCore/Data/Recovery*.swift`, `StorageMaintenance.swift`. Имена фаз и операций совпадают с §5–§7.
- `sync(2)` вызывается напрямую из Darwin, FFI не нужен; `durability` в журнале — `fsync` при успехе, `best_effort` при сбое `sync`.
- Миграция схемы остаётся как в T01.09 (`MigrationCoordinator`, снимок `VACUUM INTO` до мигратора) и не пишет отдельный журнал: её отказоустойчивость уже покрыта тестами `MigrationTests`.
- Импорт и перенос закрывают сессию, берут `StorageLock` на время файловых операций и открывают хранилище снова через `StorageCoordinator`. Между освобождением блокировки и повторным открытием есть короткое окно, которое в протоколе не описано; при сбое повторного открытия восстановление выполняется при следующем старте.
- `_safety/before-import.new` — временная копия перед заменой одной последней копии; прежняя `before-import` удаляется только после перехода в `done`.
